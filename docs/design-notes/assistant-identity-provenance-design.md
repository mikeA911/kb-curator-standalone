# Assistant Identity, Provenance & the Document-First Principle

Status: **implemented**. Reconstructed here from the original chat-pasted note (never saved as a file at the time) so a design record exists on disk, matching the other two notes in this folder.

## 1. Purpose

1. Make it clear which AI provider/model the user is talking to.
2. Preserve model provenance for Assistant conversations and outputs.
3. Establish the document-first execution principle for Workbench use cases, including two additional engineering methods: Code Review and Refactoring Plan.

Token streaming is explicitly excluded from this change.

## 2. Core Product Principle

KB Sandbox is an AI Workbench, not an autonomous software-development environment. Standard pattern: Understand → Investigate → Compare → Evaluate → Produce reviewed engineering artifact → Human takes artifact to implementation environment.

KB Sandbox may produce findings, specifications, architecture reviews, plans, review reports, test plans, guardrails, prompts, and structured handoff documents. It does **not** by default: modify the target repository, commit code, create pull requests, deploy applications, or execute arbitrary development tasks. Implementation happens externally (Claude Code, ChatGPT/Codex, Cursor, an IDE agent, a local coding agent, a conventional developer workflow, or another approved tool).

## 3. Assistant Model Identity

The Assistant UI must clearly identify the active provider and generation model, e.g. "Workbench Assistant / Groq · GPT-OSS 20B," resolved through the existing `ai_providers`/`ai_models` registry — never hard-coded.

## 4. Model Selection

If practical, allow the user to select among enabled models that support generation/chat. Must exclude disabled providers/models, embedding-only models, and models unavailable to the current environment. Changing the Assistant model must not change the configured embedding model — generation and retrieval remain independent.

## 5. Message-Level Model Provenance

Every Assistant-generated message should record which provider/model produced it — do not rely only on the current default; historical messages must remain accurate even if defaults change later. Extend `chat_messages` as necessary with references/snapshots equivalent to `provider_id`, `model_id`, `provider_name_snapshot`, `model_name_snapshot`. Follow existing KB Sandbox conventions where equivalent model provenance already exists (i.e. `wiki_versions.ai_provider`/`.ai_model`).

## 6. Conversation-Level Model Switching

A single conversation may span multiple models across different messages. Do not rewrite historical messages when the active model changes; each Assistant message retains its own model provenance.

## 7. Assistant Activity Feedback

Streaming remains deferred, but the user should get visible feedback while the Assistant is processing — minimum "Working…." Where the existing tool loop makes it practical, show more informative status: "Searching Workbench Handbook…," "Searching project knowledge…," "Checking available assessments…," "Preparing project configuration…." Do not expose hidden model reasoning/chain-of-thought — only meaningful Workbench actions. Replace the activity state with the completed response once done.

## 8. Assistant Transparency

An optional compact "Response details"/provenance affordance per response: Generated by (provider/model), Knowledge retrieval (e.g. "Platform Wiki"), Embedding model, Workbench tools used (list). Should not dominate the normal chat UX — a small Details control is sufficient.

## 9. Workbench Use-Case Principle

The Assistant should understand a Workbench use case as a method for structuring work, not necessarily an executable Agent. Generic lifecycle: User Goal → Select Workbench Method → Identify Evidence → Define Scope → Select Participant/AI/Tool → Apply Guardrail → Perform Analysis → Produce Artifact(s) → Assessment/Human Review → Approved Handoff Document → External Implementation. This principle should be represented in the Workbench Handbook so the Assistant can retrieve it rather than requiring every method to be hard-coded into its system prompt.

## 11. UC16 — Code Review

Goal: evidence-based review of an existing codebase (or defined portion), producing a structured review document for a human/dev-tool to act on. Explicitly distinct from "Code Review Comparison" (§10 item 7) — Code Review Comparison asks "how do several reviewers/models compare?"; Code Review asks "what problems and improvement opportunities exist?"

Inputs: git repo, branch, commit SHA, optional PR/diff, architecture docs, Project Wiki, coding conventions, security requirements, user-defined concerns. Repository state should be fixed where practical so findings stay reproducible.

Possible review dimensions (scope rather than requiring all): Correctness, Security, Maintainability, Architecture, Duplication, Error handling, Data access, Authorization, Performance, Observability, Test coverage, Dependency risks, Dead code, Technical debt.

Evidence requirement: findings must cite implementation evidence (Finding / Evidence / Impact / Recommendation); the AI must distinguish Confirmed / Inferred / Requires human-runtime verification.

Deliverables package: Code Review Summary, Detailed Findings, Evidence Map, Risk/Priority Matrix, Recommended Change Plan, Suggested Test/Verification Plan.

Boundary: KB Sandbox does not fix the code as part of this method. The final reviewed package becomes the implementation handoff (KB Sandbox → code-review-plan.md → Claude Code/Codex/Developer → Implementation).

## 12. UC17 — Refactoring Plan

Goal: analyze an existing application and design a safe, staged refactoring strategy without modifying the application — particularly valuable for legacy systems, where "rewrite this cleanly" would be an unsafe AI instruction.

Inputs: git repo, branch/commit, architecture docs, existing OpenAPI spec where available, MCP architecture where relevant, Project Wiki, known technical debt, business constraints, test coverage info, deployment constraints.

Analysis should attempt to determine: current architecture, component boundaries, coupling, duplicated logic, business-rule locations, data-access boundaries, auth boundaries, external integrations, high-risk areas, existing tests, missing tests, candidate service boundaries, migration dependencies.

Deliverables package: Current-State Architecture Summary, Refactoring Findings, Target Architecture, Proposed Component/Service Boundaries, Staged Refactoring Plan, Regression Risk Assessment, Required Test Coverage, Rollback/Safety Considerations, Implementation Handoff.

Staging should favor incremental change; a 7-stage example (Establish regression tests → Extract authorization/service boundary → Separate API/business logic → Consolidate duplicated data access → Refactor individual modules → Remove obsolete paths → Validate architecture and regression suite) is illustrative, not a prescribed universal sequence — the exact stages must come from the evidence.

Boundary: KB Sandbox proposes and evaluates the refactoring plan. It does not perform the refactoring.

## 13. Relationship Between Engineering Methods

Example progression for a poorly documented legacy system: Legacy System Understanding → Documentation Recovery → OpenAPI Discovery → Architecture Review → Security Review → Code Review → Refactoring Plan → MCP Architecture → Legacy Feature Introduction. Explicitly **not** a mandatory sequence — the Assistant should recommend only relevant methods (e.g. "I need someone to review this pull request" doesn't require OpenAPI Discovery first).

## 14. Document-First Handoff

Engineering methods should produce a self-contained implementation handoff document covering: Context, Objective, Evidence, Scope, Constraints, Proposed approach, Risks, Tests, Human decisions, Provenance (repo/commit, artifacts, model, and the Workbench method that produced this plan). This becomes an important Workbench artifact type — a generic concept such as **Implementation Handoff**, rather than a new artifact type per engineering method.

## 15. Assistant Behavior for Engineering Requests

For "Can you refactor this application?" the Assistant should respond conceptually with something like: "I can help set up a Refactoring Plan workstream. The Workbench will analyze the repository and produce a reviewed implementation handoff. You can then use that with your preferred coding environment to perform the changes." It should not pretend KB Sandbox can modify the repository if that capability does not exist. Similar guidance applies to "Review my application" → Code Review; "Compare Claude and Grok reviewing my application" → Code Review Comparison; "Add this user story" → Legacy Feature Introduction. This is why the Workbench Handbook should describe intent and methodology, not simply menu options.

## 16. Future Wizard Experiment

After this enhancement is implemented, do not initially seed the Assistant with the full detailed 17-use-case design as implementation logic if the objective is to test how well it understands the Workbench. Instead, the Workbench Handbook can establish the general methodology and currently implemented concepts, then the Assistant can be tested conversationally. Evaluate whether the Assistant independently recognizes concepts: Projects, Workstreams, evidence, repository/commit, multiple participants, guardrails, artifacts, assessments, prompts/versioning, human review, implementation handoff, provenance. The existing use-case design can then serve as the human reference against which the Assistant's proposal is reviewed.

## 17. Explicitly Out of Scope

Token streaming; autonomous code modification; Git commits; pull-request creation; deployment; unrestricted repository access; autonomous refactoring; autonomous implementation of user stories; automatic promotion of conversations into canonical knowledge; public MCP access; arbitrary MCP tool execution. Those remain separate future decisions.

## 18. Acceptance Criteria

1. Assistant visibly identifies active provider/model.
2. Historical Assistant messages retain actual model provenance.
3. Switching models does not alter historical provenance.
4. Generation and embedding models remain independently configured.
5. User sees a useful processing/activity indicator while waiting.
6. No token streaming introduced.
7. Workbench Handbook clearly establishes the document-first/external-implementation principle.
8. Code Review represented as a distinct Workbench method.
9. Refactoring Plan represented as a distinct Workbench method.
10. Distinction between Code Review and Code Review Comparison explicit.
11. Engineering methods produce evidence-backed artifacts suitable for external implementation.
12. Assistant never claims to have modified code when the Workbench only produced a plan.
13. Existing permissions, provenance, and human-review principles remain intact.

**Closing principle:** KB Sandbox helps people understand, evaluate, and design the work. When implementation belongs in a specialist environment, the Workbench produces an evidence-backed handoff rather than pretending to be that environment.
